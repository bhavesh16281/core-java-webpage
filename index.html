Chapter 01 — Intro to Stack and Heap

Understanding Stack and Heap Memory

Stack and Heap are two fundamental memory areas in the JVM that store data differently. Every Java developer must understand how these work to write efficient code and debug memory issues effectively.

Quick Definition: Stack stores method calls and primitive values. Heap stores actual objects and arrays. References to objects are stored in stack, but the objects themselves live in heap.

Why Two Memory Areas?

The JVM uses two memory areas because they serve different purposes:

  • Stack: For temporary, method-specific data that is deallocated automatically
  • Heap: For objects that may live longer and need flexible allocation/deallocation

Memory Allocation Example

public void example() {
  int age = 25;              // Stack: primitive value (4 bytes)
  String name = "John";      // Stack: reference | Heap: String object
  Person person = new Person(); // Stack: reference | Heap: Person object
  
  // When method ends:
  // - Stack: age, name, person references are removed
  // - Heap: Objects may remain until GC collects them
}

person →
HEAP
String: "John"
Person Object
age, name, ...

Key Insight: Stack cleanup is automatic (LIFO), but heap cleanup requires Garbage Collection.

Chapter 02 — Stack vs Heap Comparison

Side-by-Side Comparison

Stack Memory

  • Size: Fixed (1-8MB per thread)
  • Allocation: LIFO (Last-In-First-Out)
  • Speed: Very fast (pointer increment)
  • Thread: Per-thread (isolated)
  • Cleanup: Automatic (when method exits)
  • Exception: StackOverflowError
  • Stores: Primitives & references

Heap Memory

  • Size: Dynamic (configurable, typically 512MB-2GB)
  • Allocation: Flexible, scattered
  • Speed: Slower (memory search required)
  • Thread: Shared across threads
  • Cleanup: Garbage Collection
  • Exception: OutOfMemoryError
  • Stores: Objects & arrays

Practical Example: Multiple Variables

  int x = 10;
  int y = 20;
  String str1 = "Java";
  String str2 = "Memory";
  List<Integer> numbers = new ArrayList<>();

}

Chapter 03 — Why Do We Need Memory?

Understanding Stack and Heap Memory Purpose

Stack and Heap serve different purposes in the JVM. Understanding why we need both is crucial for writing efficient Java applications.

Analogy: Office vs Warehouse

Imagine you're working at an office:

Desk (Stack)

  • Size: Small
  • Speed: Very fast
  • Purpose: Current work
  • Cleanup: Automatic when work finishes
  • Access: Only by you

Warehouse (Heap)

  • Size: Large
  • Speed: Slower to access
  • Purpose: Long-term storage
  • Cleanup: Requires cleanup staff
  • Access: Shared by everyone

In Java: Stack = desk, Heap = warehouse. Both are memory areas inside the JVM process.

Technical Explanation

When a Java program runs, memory is divided into multiple regions. The two most important are Stack and Heap, and they have different purposes:

Stack Memory

  • Stores: Method execution data
  • Speed: Fast
  • Size: Small (fixed)
  • Cleanup: Automatic
  • Access: Thread-specific

Heap Memory

  • Stores: Objects
  • Speed: Slower
  • Size: Large (dynamic)
  • Cleanup: Garbage Collector
  • Access: Shared by all threads

Example: When JVM Starts

public class Main {
    public static void main(String[] args) {
        int age = 25;              // Stored in Stack
        Person p = new Person();   // Object in Heap, reference in Stack
    }
}

Two things happen:

  • age → Stored in Stack (primitive value)
  • new Person() → Object stored in Heap
  • p → Reference stored in Stack (points to object in Heap)

Visual Representation

STACK
age = 25
p →
HEAP
Person Object
name: "John"
age: 25
address: "..."

Important Notice: The actual object is NOT in the stack. Only the reference is. This is one of the most frequently asked interview questions.

Rule #1: Primitive Variables → Stack

Primitive local variables are stored directly inside stack frames:

int a = 10;
double salary = 5000;
char grade = 'A';
boolean active = true;

// All stored directly inside stack frames

Rule #2: Objects → Heap

Objects are created using the new keyword and stored in Heap:

Student s = new Student();

// Object: Student        → Heap
// Reference: s          → Stack

Why Not Store Objects in Stack?

Consider this example:

Employee e = new Employee();

// Employee contains:
String name;
String address;
List<Project> projects;

// Object size becomes unpredictable!

Problems with storing objects in Stack:

  • Object size is unknown at compile time
  • Stack memory must stay fast and simple
  • Stack frames have fixed size per method

Solution: Stack stores references (small, fixed size). Heap stores actual objects (large, variable size).

Internal Working: Stack Frames

When a method is called, JVM creates a stack frame to hold local variables:

public void calculate() {
    int a = 10;
    int b = 20;
}

Before method call:

STACK
main()

During calculate() call:

STACK
calculate()
a = 10
b = 20
main()

After method returns:

STACK
main()
← calculate() frame destroyed

Key Point: When a method finishes, its stack frame is destroyed automatically. No garbage collection required. This is why stack is so fast!

What Happens When You Run java Hello?

Most developers stop at knowing the three components. But understanding what happens inside JVM step-by-step is what separates average candidates from strong ones.

01
OS Creates a New Process

When you run java Hello, the OS creates a process — just like chrome.exe or notepad.exe. Inside this process, the JVM starts up.

02
JVM Allocates Runtime Memory Areas

Before loading any code, JVM sets up its internal memory regions:

Heap Stack Method Area PC Register Native Method Stack
03
Class Loader loads Hello.class

The Class Loader locates the .class file and loads it into the Method Area of JVM memory.

04
Bytecode Verifier checks safety

Before execution, the verifier validates the bytecode: is it well-formed? Are memory accesses safe? Is the stack usage legal?

05

The Execution Engine (via Interpreter + JIT Compiler) translates bytecode to machine code and the CPU executes it.

Chapter 13 — All 5 Memory Areas

JVM Memory Layout

Every JVM memory area has a specific role. Interviewers often ask about all five.

Heap 🏭

Stores all objects and arrays created at runtime.

Employee e1 = new Employee();
Employee e2 = new Employee();
// Both objects → Heap
Stack 🍽️

Each thread has its own stack. Stores method call frames and local variables like emp.

Employee emp = new Employee();
// emp reference → Stack
// object itself  → Heap
Method Area 📐

Stores class metadata, field/method info, static variables, runtime constant pool. Shared across threads.

One Employee class definition → Method Area
Many Employee object instances → Heap

PC Register 📖

Like a bookmark in a book — tracks which bytecode instruction a thread is currently executing. Each thread has its own PC Register.

Stores the address of the current JVM instruction being executed by a thread.

Native Method Stack ⚙️

Used when JVM calls methods written in C or C++ (native methods). Examples: Thread.start(), System.arraycopy().

public native void start();
// "native" = outside Java

Answer: All class metadata, static variables, static blocks.
Interview-Grade Answer Method Area stores class metadata such as class name, method information, field information, static variables, runtime constant pool, and other class-level information.
✅ Correct What is the purpose of the PC Register?

At this stage, you're thinking about the JVM as a system — not just memorising definitions. Here's a careful evaluation.

✅ Correct Why does Java generate bytecode instead of machine code directly?

Chapter 18 — One of the Most Asked JVM Topics

Parent Delegation Model

This comes up surprisingly often in interviews. Understanding it shows you think about JVM security and architecture, not just definitions.

The Problem It Solves

Your app has String str = "Hello" — loaded by Bootstrap. It also has Employee emp = new Employee() — loaded by Application Loader. The question is: how do they cooperate without loading the same class multiple times, and how does Java prevent someone replacing core classes like String?

🏢 Real World Analogy

In a company, when an employee gets a task, they ask the manager first. Manager asks the director. Only if everyone above fails does the employee handle it themselves.

Director
↑ asks first
Manager
↑ asks first
Employee ← receives task
☕ JVM Class Loader Hierarchy
Bootstrap Class Loader
Loads core Java classes: String, Object, System, Thread
from rt.jar / core modules
↑ delegates to parent
Platform Class Loader
Loads Java extension / platform classes
from $JAVA_HOME/lib/ext
↑ delegates to parent
Application Class Loader
Loads your classes: Employee, Student, Hello
from application classpath

How It Works — Step by Step

1 Application Loader receives request: "Load String.class"
2 Does NOT load immediately. Asks parent: Platform Loader
3 Platform Loader asks its parent: Bootstrap Loader
4 Bootstrap says "I know String.class" and loads it ✓
5 If Bootstrap couldn't, Platform tries. If Platform can't, Application loads it itself.

Why Is This Critical for Security?

⚠️ Without Parent Delegation
java/lang/String.java (malicious) 
package java.lang;
public class String {
    // Malicious override of Java's String!
    // Could steal data, crash JVM, etc.
}

Without delegation, a rogue class could replace java.lang.String. Parent Delegation prevents this — Bootstrap always loads core classes first.

🎤 Interview Definition

Parent Delegation Model is the class loading mechanism where a class loader delegates class loading requests to its parent before attempting to load the class itself. This prevents core Java classes from being overridden by application code.
